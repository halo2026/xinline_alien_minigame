# 0029 第一关绘制与清场内存优化

用户反馈VIVO X80第一关第二幕掉帧、中上部慢底部快；另一台苹果手机仍在打扫战场时闪退（已通过异步问答确认，不是切关才闪退，型号未知）。用户要求改好发布体验版。

## 已证实问题与改动

- 本机原生Canvas390×844固定位置基线：y500约9.87ms，y1000约9.85ms，y1700约7.28ms。中部可见60道具、底部38；底部没有可见虫洞。虫洞每帧重复裁剪及32颗碎石，单层计时约0.44ms，缓存后约0.03～0.04ms；不将桌面测量当手机FPS。
- drawSpawnCave保留原source实现，小尺寸240×224离屏背/前层按出生点缓存，仍按原前后遮挡顺序绘制。游戏切换时释放旧块，离屏不可用回退原绘制。截图与像素误差验证通过。
- 原山崖2170×2227缓存19,330,360字节，改1628×1671后10,881,552字节（18.4→10.4MiB），世界坐标尺寸保持。实际地形叠加后的玩法缩放图像平均通道差<2/255；这是缓存降采样，不再声称逐像素完全一致。源图保留，运行每帧仍1drawImage。
- 尝试稀疏外露崖面图集仍需1.5MB下载、约13.8MiB解码，不适合包体和收益；未采用，删除本次临时工具与资源。
- 无尸体时不分配全地图污渍Canvas，已有空层缩至1×1释放。正常有尸体保持原缓存逻辑。
- 结算原先清bullets但保留trails，尾迹仍引用停止推进的子弹及hit目标；清bullets的胜利/幕结算和第二幕初始化同时清trails，避免清场阶段保留这些对象。
- scene-cache模块负责切关前将旧山崖/污渍/地形等Canvas缩至1×1，成功后图片Promise缓存仅保留当前关卡用到文件；失败时旧场景可重新生成画布，保留存档。手动重来同步释放。没有修改玩家进度KEY/epoch。
- 第一关全图集115页RGBA尺寸估算269,309,328字节（约257MiB），不代表实机实际占用或峰值；这部分仍然较高，不能宣称苹果崩溃根因完全确认。没有崩溃日志，仍需手机复测。
